# 02 — Backend request lifecycle

This document follows one GraphQL request all the way down and back, and then covers the
four backend mechanisms that most often surprise people: **transactions**, **plugin
hooks**, **partial-update translation**, and **lazy relationship loading**.

## Read path: `findScene(id: 5)`

```
  POST /graphql
        │
        ▼
  chi router ──► gqlgen handler ──► internal/api/generated_exec.go
        │
        │  gqlgen parses + validates against the schema, then dispatches
        ▼
  queryResolver.FindScene(ctx, id)          internal/api/resolver_query_find_scene.go
        │
        │  r.withReadTxn(ctx, func(ctx) { ... })      ← puts a *read* txn on the context
        ▼
  r.repository.Scene.Find(ctx, 5)           pkg/sqlite/scene.go
        │
        │  goqu SELECT ... FROM scenes WHERE id = ?
        ▼
  *models.Scene  — scalar columns populated, relationships NOT loaded
        │
        ▼
  returned to gqlgen, which now resolves each requested *sub-field*
        │
        ├─ scene.tags      ──► sceneResolver.Tags(ctx, obj)   resolver_model_scene.go
        │                        └─► loads obj.TagIDs, then dataloader-batches Tag fetches
        ├─ scene.performers──► sceneResolver.Performers(...)
        ├─ scene.files     ──► sceneResolver.Files(...)
        └─ ...
        │
        ▼
  JSON response
```

The key thing: **the store returns a shallow object**. Every relationship is fetched
later, by a *field resolver*, only if the query asked for it. Two mechanisms make that
efficient — read on.

### Field resolvers and the N+1 problem

If you query 40 scenes and each resolves `studio`, you'd naively issue 40 studio queries.
Stash avoids this with **dataloaders** (`internal/api/loaders/`), generated by
`vektah/dataloaden` via `make generate-dataloaders`.

A loader batches keys arriving within a 1ms window, up to 100 keys
(`internal/api/loaders/dataloaders.go` — `wait`/`maxBatch`), then issues one
`FindMany` call.

```
  40 concurrent field resolvers all call loaders.SceneByID.Load(id)
                 │
                 │  (batched for 1ms, max 100 keys)
                 ▼
        one SceneStore.FindMany(ctx, [40 ids])
                 │
                 ▼
        results fanned back out to each caller
```

Loaders live on the **request context** (`loaders.From(ctx)`), so the cache lifetime is
one HTTP request. That's intentional: it means no cross-request staleness.

⚠️ **Dataloaders and transactions interact badly if you're careless.** A loader's batch
function runs its own database access. If you call a loader from inside a write
transaction that has uncommitted changes, the loader may not see them. Field resolvers
run *after* the mutation's transaction has committed, which is why the pattern in the
write path (below) re-fetches the object after the txn closes.

## Write path: `sceneUpdate`

This is the canonical mutation shape — `internal/api/resolver_mutation_scene.go:122`:

```go
func (r *mutationResolver) SceneUpdate(ctx context.Context, input models.SceneUpdateInput) (ret *models.Scene, err error) {
    translator := changesetTranslator{ inputMap: getUpdateInputMap(ctx) }   // 1

    if err := r.withTxn(ctx, func(ctx context.Context) error {              // 2
        ret, err = r.sceneUpdate(ctx, input, translator)
        return err
    }); err != nil {
        return nil, err
    }

    r.hookExecutor.ExecutePostHooks(ctx, ret.ID,                            // 3
        hook.SceneUpdatePost, input, translator.getFields())

    return r.getScene(ctx, ret.ID)                                          // 4
}
```

Four steps, and **all four matter**:

```
 1. changesetTranslator     capture WHICH fields the client actually sent
 2. withTxn                 do the write, atomically
 3. ExecutePostHooks        fire plugin hooks — AFTER commit, OUTSIDE the txn
 4. getScene (re-fetch)     hooks may have mutated the scene; return fresh data
```

Step 3-and-4 is the part people omit when adding a new mutation. If you fire hooks inside
the transaction, a plugin that writes to the database will deadlock against the single
writer connection (doc 04). If you skip the re-fetch, the client gets pre-hook data.

For **batch** mutations (`ScenesUpdate`), the whole loop runs in *one* transaction, then
hooks fire per-item afterwards — see `resolver_mutation_scene.go:139-180`.

## Mechanism 1 — transactions

`pkg/txn` is a thin, well-behaved wrapper. Two entry points:

| Helper | Writable | Use for |
|---|---|---|
| `r.withReadTxn(ctx, fn)` | no | every query resolver |
| `r.withTxn(ctx, fn)` | yes | every mutation resolver |

The transaction is carried **on the context**, not passed as a parameter. Store methods
take `ctx` and pull the transaction out of it. This is why every store method's first
argument is `context.Context` and why you must never stash a `ctx` beyond the txn's life.

`pkg/txn/transaction.go:52` shows the full contract:

```
  begin
    │
    ├─ fn(ctx) returns error ──► rollback ──► post-rollback hooks ──► post-complete hooks
    │
    └─ fn(ctx) returns nil   ──► commit   ──► post-commit hooks   ──► post-complete hooks
                                                    ▲
                                          registered via txn.AddPostCommitHook(ctx, fn)
    (a panic rolls back and re-panics)
```

**Post-commit hooks are the correct place for side effects that must not happen on
rollback** — cache invalidation, file deletion, notifying the plugin system. Register
them from inside the transaction; they run outside it with the *outer* context.

## Mechanism 2 — `changesetTranslator` (partial updates)

GraphQL cannot distinguish "field omitted" from "field explicitly set to null" using Go
types alone — both arrive as a nil pointer. Stash solves this by inspecting the raw
argument map that gqlgen keeps on the context.

`internal/api/changeset_translator.go:23`:

```go
func getUpdateInputMap(ctx context.Context) map[string]interface{}
```

This returns the literal keys the client sent. The translator then offers methods that
produce an `Optional*` value:

```
  client sent  { "title": "x" }           → translator.optionalString(...)  → Set("x")
  client sent  { "title": null }          → translator.optionalString(...)  → Set(null)  (clears it)
  client omitted "title" entirely         → translator.optionalString(...)  → NotSet     (leaves it alone)
```

These feed the `*Partial` structs (`models.ScenePartial`, `pkg/models/model_scene.go:70`)
whose fields are `OptionalString`, `OptionalInt`, `OptionalBool`, etc. The store then
only emits `SET` clauses for fields that are `Set`.

⚠️ **If you add a field to an `*UpdateInput` GraphQL type, you must also add it to the
matching `*Partial` struct as an `Optional*` and translate it in the resolver.** Skipping
this silently makes the field un-updatable — no error, it just never persists.

`translator.getFields()` returns the list of changed field names, which is passed to
plugin hooks so a plugin can react to *what* changed.

## Mechanism 3 — relationship updates (`UpdateIDs`)

Many-to-many edits don't take a plain list. They take an operation
(`pkg/models/update.go:54`):

```go
type UpdateIDs struct {
    IDs  []int
    Mode RelationshipUpdateMode   // SET | ADD | REMOVE
}
```

- `SET` — replace the whole list
- `ADD` — union with existing
- `REMOVE` — subtract from existing

`Apply(existing)` computes the result; `ImpactedIDs(existing)` computes only the rows that
actually change, which is what hook notifications and cache invalidation use. Use
`ImpactedIDs` when you need "what did this touch", not `IDs` — the client may have sent
IDs that were already present.

`UpdateGroupDescriptions` is the same idea for group membership, where `ADD` *overwrites*
an existing entry with the same group ID rather than duplicating it
(`pkg/models/update.go:157`).

## Mechanism 4 — lazy relationships (`RelatedIDs`) and the panic

This is the single most surprising thing in the backend.

```go
type Scene struct {
    // ...
    TagIDs       RelatedIDs
    PerformerIDs RelatedIDs
    GalleryIDs   RelatedIDs
    Groups       RelatedGroups
    StashIDs     RelatedStashIDs
}
```

A `RelatedIDs` holds `list []int`. Its contract (`pkg/models/relationships.go:85`):

- `Loaded()` — true iff `list != nil`
- `List()` — **panics** if not loaded
- `Add()` — **panics** if not loaded

```
  scene := store.Find(ctx, 5)
  scene.TagIDs.List()          ← PANIC: "list has not been loaded"

  scene.LoadTagIDs(ctx, loader)  // or the store's LoadRelationships
  scene.TagIDs.List()          ← []int{1, 7, 9}
```

The panic is deliberate: it converts "silently returned an empty list" — a bug that ships
— into "crashed loudly in dev". Respect it. When you write code that reads a
relationship, either call the matching `Load*` method first, or check `Loaded()`.

The loader interfaces are all declared at the top of `pkg/models/relationships.go`
(`TagIDLoader`, `PerformerIDLoader`, `SceneGroupLoader`, `StashIDLoader`, …). The SQLite
stores implement them, so `scene.LoadTagIDs(ctx, r.repository.Scene)` is the usual call.

`NewRelatedIDs(ids)` constructs a *loaded* one — this is how mutation resolvers build an
object whose relationships are known up front. Note `NewRelatedIDs(nil)` produces an
**unloaded** one, which is occasionally what you want and occasionally a bug.

## Plugin hooks

```
  hook.TriggerEnum values                  pkg/plugin/hook/
  ────────────────────────────────
  Scene.Create.Post / Update.Post / Destroy.Post
  Image.*  Gallery.*  GalleryChapter.*  SceneMarker.*
  Performer.*  Studio.*  Tag.*  Group.*  Movie.* (legacy alias)
  Scan.Post, and other task-completion triggers
```

`r.hookExecutor.ExecutePostHooks(ctx, id, trigger, input, changedFields)` dispatches to
every plugin registered for that trigger. Plugins are external processes (raw exec or
RPC) or JS. They run **synchronously** — a slow plugin slows down your mutation.

There are no `*.Pre` hooks. If you need to veto an operation, that's a service-layer
validation change, not a hook.

## Where to put new backend logic

```
  Is it request/response translation, or txn/hook orchestration?
      └─► resolver  (internal/api/resolver_*.go)

  Is it a business rule for Scene / Gallery / Image / Group?
      └─► service   (pkg/scene, pkg/gallery, pkg/image, pkg/group)

  Is it a business rule for Performer / Studio / Tag?
      └─► validation function in pkg/performer, pkg/studio, pkg/tag,
          called from the resolver (these entities have no service layer)

  Is it "how do I read/write this in SQL"?
      └─► store     (pkg/sqlite/*.go)

  Is it a filter or a sort?
      └─► pkg/sqlite/<entity>_filter.go  — see doc 03
```

⚠️ Resolvers must not contain business rules, and stores must not contain business rules.
The most common review comment on Stash PRs is logic that belongs in a service sitting in
a resolver. If Performer/Studio/Tag needs real logic, it's reasonable to *introduce* a
service package for it rather than fatten the resolver.
