# First upstream merge, with fork migrations in a stream of their own and fork server code reduced to call sites

**Merged:** 2026-10-24 · `upstream-sync/20261024` into `main-sugoi-ahegao` as `8cf477772` · 6 fork commits + 1 upstream merge · not known whether it was shipped

_Written on 2026-11-13, after the merge, from git history; the entries convention didn't
exist yet._

The fork's first upstream merge. It needed preparation: the fork's one migration was
numbered so that it would have hidden upstream's next one, and its server changes sat
inside upstream functions. Six commits fixed that, then `scripts/upstream-sync` merged
upstream on branch `upstream-sync/20261024`, and main was fast-forwarded to the merge.

## What changed

- **Everything upstream stash added between `v0.31.1-132` and `v0.31.1-176`** (44 commits,
  merged at `bdee3c83d`): among them a production date on scenes (#6533, upstream
  migration 86), the saved filter list refactor (#7224), improved scraper search (#7259),
  "Select by Codec" in the duplicate checker (#5281), remote duration in the tagger
  (#7193), more patchable components and plugin UI hooks, and a 5s database busy timeout
  (#7190). Upstream's notes are in `ui/v2.5/src/docs/en/Changelog/`.
- **Nothing changes in how the fork's features behave.** The rest is how they're stored
  and wired.
- **The fork's database migration now runs in its own stream.** On first open, a
  database at the old numbering is converted (upstream version 85, fork version 1), and
  upstream's migration 86 then runs through the ordinary migrate page.

## How it works

- **Two migration streams** (`c77c887cc`): fork migrations live in
  `pkg/sqlite/migrations_fork/`, numbered from 1, tracked in `fork_schema_migrations`, and
  run from `initialise()` once upstream's schema is current, after a backup that's
  restored if they fail. The view-history migration became
  `migrations_fork/1_scene_view_history.up.sql`. Upstream's migrator is upstream's code
  again; the fork's footprint in `database.go` is three `// fork` lines. Details:
  `docs/codebase/12-upstream-sync.md` and
  [decision 0001](../decisions/0001-fork-migration-stream.md).
- **Call sites, not edits** (`35bc891b3`): `featuredTracker` in
  `internal/api/scene_featured.go` wraps upstream's `sceneUpdate` instead of changing its
  signature, and the view mutations moved to `resolver_mutation_scene_view.go`.
  `resolver_mutation_scene.go` went from 163 fork lines to a few marked call sites
  ([decision 0002](../decisions/0002-fork-code-at-call-sites.md)).
- **`scripts/upstream-sync`** (`7726f769d`): merges `upstream/develop` in a worktree of its
  own, settles generated files, regenerates mocks, checks the fork's migration rules,
  builds, runs unit and integration tests and commits the merge.
- **`scripts/prod`** (`f70bf6b0e`): ships a checkout to the Windows production `stash.exe`
  and pulls production data into dev. Doc 11 describes the layout.
- **The merge itself** had one conflict, in `Scene.tsx`'s imports (the fork's golden and
  featured helpers against upstream's `useMonitorJob`); both were kept.

## Tried and changed

- **Numbering the fork's migration 185 in upstream's table** (2026-09-21) was the first
  approach. golang-migrate keeps one version per table, so a database at 185 would have
  skipped upstream's new 86 without an error and failed on the first query that touched
  the new column. The non-contiguous-versions change that supported it (`dafff9c09`) was
  reverted.
- **The stash-box client regeneration** of 2026-08-28 (`fa0ee396c`) was reverted
  (`fa3a2a3df`). It's generated from stashdb.org's live schema, so a regeneration in the
  fork only conflicts with upstream's next one, and nothing used the new types.
- **A rehearsal merge** was run first on a throwaway commit of the working tree (both
  survive only as unreachable objects). Per doc 07, it had no server-side conflicts.
- **`scripts/preview`**, added here for per-branch preview servers, was replaced the same
  day by per-worktree libraries and ports (`d77ff7009`, `a441988bb`), and doc 09's
  shared-library setup was superseded by doc 11.

## Watch out

- **Converted databases can't go back.** A build from before this change reads version 85,
  tries to migrate to 185, fails on the existing table and restores its backup. Ship this
  everywhere and don't roll back past it.
- **Fork migrations only create tables of their own**, never alter upstream's, because
  upstream rebuilds tables by copying only the columns it knows. `scripts/upstream-sync
  check` enforces the rules.
- `pkg/stashbox/graphql/generated_models.go` is upstream's: take theirs on every merge.
- The export test needed `GetViewedDates` added to its mock (`602045543`); it had panicked
  since view history landed.
